# Agent 工作流改造验收：如何度量

这次改造的目标不是压缩 JSON 字符，而是**缩小 Agent 每次读写的数据范围**。
用同一批代表性任务，在改造前后各跑一遍，比较以下指标。

## 代表性任务

- 单任务推进：`RG-023`（有依赖、需要证据和审计）；
- 被拒绝后恢复：对一个硬依赖未完成的任务尝试 `complete`；
- 跨任务查询：找当前可开工任务并选择下一个目标；
- 长任务交接：为进行中任务生成交接摘要，新会话接续。

## 指标与采集方式

| 指标 | 采集方式 |
|---|---|
| 输入 token | Agent 会话日志中每次模型调用的 prompt 大小之和（改造前主要是每次读 `project.json` 的全文） |
| 输出 token | 模型改状态时回显的 JSON 大小（改造后是 `{ok,id,changed,next}` 短回执） |
| 工具调用次数 | 完成同一任务所需的读/写操作次数（改造后 `context → evidence add → submit-audit → handoff` 共 4 次左右） |
| 重试次数 | 因格式错误、字段拼错、规则误判导致的失败重试 |
| 结果正确率 | 事实源 diff 是否只包含预期变更；`task validate` 是否通过 |

## 预期

- 读取：从「每次全量 21KB project.json + 自行推理规则」变成「单任务 context 约 1KB + 程序裁决」；
- 写入：从「回显整段 JSON」变成「<10 行短回执」；
- 噪声：`git add`/`git commit` 不再进入共享活动历史，事件按业务身份去重后不随重试膨胀。

数字本身不重要；重要的是确认「每次读整张图」已经变成「只读当前任务」，
以及规则类错误（硬依赖、审计门槛）降为零——那些现在由脚本拒绝并给出错误码。
